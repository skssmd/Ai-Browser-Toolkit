# What gets logged, where it lives, and what it can answer

Four independent record layers. They overlap on purpose: when a number looks
wrong, you check it against a layer written by different code.

The rule for choosing between them: **the sweep layer knows what happened
across episodes, the toolkit layer knows what happened inside one.**

---

## The four layers at a glance

| layer | written by | lives | one row/file is | answers |
|---|---|---|---|---|
| sweep results | `sweep_webarena.py` | `toolkit/results/<sweep>/` | one episode | did it pass, what did it cost |
| task traces | `loop_policy.py` | `results/<sweep>/traces/` | one episode | what the model was thinking |
| toolkit session | `abt serve` | `~/.local/state/aibrowsertoolkit/logs/` | one command | what the browser was asked and answered |
| analytics | `dashboard.py` | memory, served on `:9102` | the whole run | how it is going, right now |

---

## 1. Sweep results — `toolkit/results/<sweep>/`

```
plan.json          the commitment: model, ports, ceiling, exact task list
episodes.jsonl     one JSON row per episode, appended as it finishes
raw/<task>.json    the same row, plus the long fields
traces/<task>.log  turn-by-turn narrative (see layer 2)
report.md          generated by `sweep_webarena.py report`
```

### `plan.json` — written once, before anything runs

`model`, `provider`, `server`, `cdp_port`, `trace_port`, `max_turns`,
`sites_running`, `task_ids`, `episodes`. This is what makes a result
reproducible, and why the runner refuses to overwrite one without `--force`:
rewriting the plan after a run invalidates the results.

### `episodes.jsonl` — the metrics, one line per episode

Scoring, from WebArena and not from us:

| field | meaning |
|---|---|
| `reward`, `success` | WebArena's verdict. `success` is `reward > 0` |
| `status` | `ok`, `harness_error`, `harness_timeout`, `skipped_site` |
| `judge` | `ok`, `unavailable` (no GPT judge for `fuzzy_match`), `fallback` |
| `hit_turn_limit` | the ceiling stopped it, rather than the agent finishing |

Cost and behaviour, ours:

| field | meaning |
|---|---|
| `turns` | model round trips — **the number cost scales with, squared** |
| `ops`, `op_failures`, `op_success_rate` | did the agent drive the toolkit correctly |
| `ops_per_turn` | is it batching; 1.00 means it never did |
| `input_tokens`, `output_tokens`, `total_tokens` | what it cost |
| `cache_read_tokens`, `cache_share` | how much input was a cached re-read |
| `wall_s`, `model_s` | total time, and time waiting on the model |

Enough to re-judge later without re-running:

| field | meaning |
|---|---|
| `goal` | the task as the agent was given it |
| `reply` | the model's full final message |
| `answer_sent` | just the `ANSWER:` line, which is what was scored |
| `scored_action` | the literal action the evaluator saw |
| `eval_types`, `reference_answer` | how it was meant to be scored, and against what |
| `final_url` | where the browser ended up |

Those last six are why a judging pass is possible at all. They are gathered
**before** `env.close()` — BrowserGym deletes the task config on close and the
browser goes with it, so gathering afterwards silently yields `None`, the kind
of empty field nobody notices until the judging pass has nothing to judge.

### Two traps when reading `episodes.jsonl`

**A retried task has more than one row.** Counting all of them reports one task
as both a failure and a pass. Use `dedupe_rows(read_rows(out))` — it keeps the
settled row, else the latest attempt.

**`status: ok` is not the same as "the agent tried and failed".** An episode
with `judge: "unavailable"` ran fine and simply could not be scored. Excluding
those from a pass rate is the honest choice; including them understates it.

## 2. Task traces — `results/<sweep>/traces/<task>.log`

The narrative: what the model thought, what it said, what ops it sent, what
the page gave back.

```
--- turn 16 -------------------------------------------
  [think] Now click Show Report and then get_html of the filter inputs.
  [ops  ] sending 3:
          click        {'text': 'Show Report'}
          get_html     {'css': '#sales_report_from'}
          get_text     {'css': '#sales_report_grid'}
  [back ] 3 ops, 1 FAILED
=== done: 9 turns, 11 ops, 103,850 tokens (85,824 cached) ===
```

Written **line by line as the episode runs**, line-buffered, so a task that
hangs or is killed still leaves everything it had said. The same content is
served live on `:9100`/`:9101` while the episode is running — the file is what
survives it.

This is the layer that explains *why* a number is what it is. Every failure
diagnosis in this project came from reading one of these.

## 3. Toolkit session logs — `~/.local/state/aibrowsertoolkit/logs/<session>/`

```
events.jsonl   one entry per command: request, response, timing, tab, url
shots/         a screenshot per command
meta.json      session id and settings
```

Written by `abt serve`, one session directory per server start. Independent of
the benchmark entirely — it records what the browser was asked and what it
answered, whoever asked.

Reachable in a browser at `<server>/viewer`, which replays commands and
responses with the screenshots inline.

**Three things to know before trusting it:**

- **Responses are truncated at roughly 4.2 KB.** Fine for seeing what an op
  returned; useless for measuring how large a response was. Measure that at
  the wire instead.
- **The stored `response` is the result object itself**, not an `{ok, result}`
  envelope. Reading it as an envelope makes every entry look like a failure.
  That mistake produced a phantom "`run_js` never returns a value" bug here.
- **A new directory per server restart.** Restart a server and the trail
  continues in a new session; the traces in layer 2 have no such seam.

## 4. Analytics — `dashboard.py` on `:9102`

Derived, not stored. Recomputes every 180s from `episodes.jsonl` and
`plan.json`, holds the result in memory, serves it as a page and as
`GET /data`. Nothing here is a source of truth — it is the other layers,
totalled.

Use it to watch. Use `episodes.jsonl` to make a claim.

---

## Which layer answers which question

| question | look at |
|---|---|
| what is the pass rate right now | `:9102`, or `sweep_webarena.py report` |
| did *this* task pass, and what did it cost | `episodes.jsonl` |
| why did it fail | `traces/<task>.log` |
| what exactly was the answer, and what was expected | `raw/<task>.json` |
| what did the browser actually return for one op | `events.jsonl` + `/viewer` |
| what did the page look like at that moment | `shots/` |
| what configuration produced these numbers | `plan.json` |

---

## Roughly what it costs to keep

At ~180 episodes: results ~1 MB per sweep, toolkit session logs ~31 MB
(screenshots dominate). Small enough to keep all of it, and the reason any
claim in this project can be checked rather than taken on trust.
